## 1. Executive Summary

인프라 엔지니어 1명이 AI(Claude)와 협업하여, 분산된 Grafana 대시보드와 엑셀 기반 자산관리를 대체하는 **통합 DCIM 웹 애플리케이션 "DC Express"**를 4개월 만에 구축했다.

**핵심 성과**: 39개 페이지, 73개 API, 29개 DB 모델, 134개 구현 기능, 43,974줄 코드. 513커밋 중 99%를 AI가 작성했으며, 실질 개발 기간은 약 2.5개월이다. 서버 모니터링, 자산 라이프사이클 관리, Digital Twin 물리배치, 용량 예측, BMC 원격 제어, K8s 워크로드 통합까지 — 기존에 5개 이상의 도구로 흩어져 있던 업무를 하나의 웹 화면에서 처리할 수 있게 되었다.

## 2. 배경: 왜 만들었나

### 기존 환경의 문제

우리 팀의 데이터센터 운영은 여러 도구에 의존하고 있었고, 각 도구가 분리되어 있어 통합적인 인프라 파악이 어려웠다.

**1) Grafana 대시보드 산재**

서버 모니터링을 위해 Grafana를 사용하고 있었지만, 대시보드가 10개 이상으로 흩어져 있었다. CPU를 보려면 A 대시보드, 온도를 보려면 B 대시보드, 네트워크를 보려면 C 대시보드를 열어야 했다. 한 화면에서 특정 서버의 전체 상태를 파악하는 것이 불가능했고, 새벽에 장애가 나면 여러 대시보드를 오가며 원인을 추적해야 했다.

**2) 엑셀/수기 자산관리**

장비 대장(호스트명, IP, 모델명, 구매일, 보증 만료일 등)을 엑셀 파일로 관리했다. 장비가 추가되면 누군가가 엑셀에 한 줄 추가하고, 수리 보내면 상태를 수동으로 바꾸고, 폐기하면 행을 삭제했다. 버전 관리가 안 되니 "최신 파일이 어느 건지" 혼란이 생겼고, 보증 만료일은 아무도 체계적으로 추적하지 않았다.

**3) 물리 배치를 머릿속으로 기억**

"GNR-05 서버가 어느 랙 몇 U에 있지?"라는 질문에 대한 답은 담당자의 기억에 의존했다. 랙 배치도를 그려둔 문서가 있었지만 최신 상태를 반영하지 못했고, 장비 24대를 한꺼번에 입고하면 배치 계획을 종이에 그려가며 세워야 했다.

**4) 개발 자원의 부재**

이 문제들을 해결할 웹 애플리케이션이 필요했지만, 팀에 전담 웹 개발자가 없었다. 외주를 맡기자니 데이터센터 도메인 지식 전달이 어렵고, 비용도 수천만 원 수준이었다. 이 상황에서 AI 협업 개발(바이브 코딩)이라는 새로운 가능성을 시도하게 되었다 — 인프라 엔지니어가 도메인 지식을 제공하고, AI가 코드를 작성하는 방식이다.

## 4. 주요 기능과 사용 시나리오

기능 목록을 나열하는 대신, 실제 업무에서 이 시스템을 어떻게 사용하는지 세 가지 시나리오로 설명한다.

### 시나리오 A: "새벽 3시, 서버 장애 알림"

> *새벽 3시에 알림이 울린다. GNR-12 서버의 CPU 온도가 임계값을 초과했다.*

**기존 방식**: Grafana 알림 확인 → 어떤 서버인지 확인 → 온도 대시보드 이동 → CPU 대시보드 이동 → IPMI로 별도 접속 → 상태 확인 → 필요시 재시작

**DC Express에서의 흐름**:

1. **알림 확인** (`/alerts`): 활성 알림 목록에서 "GNR-12 CPU Temperature Critical" 확인. 심각도/카테고리가 바로 보인다.

2. **서버 상세 진입** (`/servers/[id]`): 알림에서 서버를 클릭하면 CPU 사용률, 메모리, 온도 차트, PCIe 대역폭이 한 화면에 나온다. 시간 범위(15분/1시간/6시간/24시간/7일)를 바꿔가며 언제부터 온도가 올랐는지 추적한다.

3. **BMC 센서 확인** (같은 페이지 하단): Redfish를 통해 BMC 온도 센서(Inlet/Outlet/CPU 각각), 팬 RPM, 전력 소비를 실시간으로 확인한다. 팬이 정상인데 온도가 높으면 워크로드 과부하, 팬 RPM이 낮으면 하드웨어 문제.

4. **원격 전원 제어** (`POST /api/equipment/[id]/power`): 필요시 웹에서 바로 서버 재시작(Graceful Restart). 별도 IPMI 접속 없이 한 화면에서 처리.

5. **복구 확인**: 재시작 후 CPU/온도 차트가 정상으로 돌아오는지 실시간 모니터링. 알림을 "확인(Acknowledge)" 처리.

**관련 시스템 구성**: 이 흐름에서 Prometheus(메트릭 시계열), PostgreSQL(장비 정보, 알림 이력), BMC/Redfish(센서, 전원 제어) 세 가지 데이터 소스가 하나의 화면에서 통합된다. API는 `GET /api/metrics/range`(시계열 차트), `GET /api/equipment/[id]/sensors`(BMC 센서), `POST /api/alerts/[id]/ack`(알림 확인) 등이 사용된다.

[스크린샷: 서버 상세 페이지 - CPU/온도/BMC 센서가 한 화면에 표시된 모습]

---

### 시나리오 B: "장비 24대 입고"

> *Lab-3에 신규 서버 24대가 도착했다. 자산 등록부터 모니터링 시작까지 진행해야 한다.*

**기존 방식**: 24줄을 엑셀에 타이핑 → 각 서버 IP/호스트명 메모 → Grafana 대시보드에 수동 추가 → 랙 배치를 종이에 그림 → 담당자에게 구두 전달

**DC Express에서의 흐름**:

1. **CSV 일괄 등록** (`/infrastructure/import`): 호스트명, IP, 모델, 시리얼번호가 담긴 CSV 파일을 업로드한다. 미리보기 화면에서 24대의 데이터를 검증하고, 오류가 있으면 수정한 뒤 한 번에 등록한다.
   - API: `POST /api/equipment/bulk` (CSV 파싱 + 유효성 검증 + 일괄 INSERT)

2. **Prometheus 자동 탐지** (`/settings/discovery`): Prometheus의 `/api/v1/targets`에서 새로 등록된 서버들의 node-exporter를 자동으로 감지한다. "미등록" 필터로 24대를 확인하고, 일괄 매핑으로 장비와 연결한다.
   - API: `GET /api/discovery/targets`, `POST /api/discovery/register`

3. **BMC 하드웨어 자동 수집** (`POST /api/equipment/[id]/refresh-hw`): 각 서버의 BMC(Redfish)에 접속하여 CPU 모델, 코어 수, 메모리 용량, NIC 정보를 자동으로 가져온다. 수작업으로 스펙을 타이핑할 필요가 없다.

4. **랙 배치** (`/racks`): 랙 시각화 화면에서 미배치 장비 24대를 드래그&드롭으로 원하는 랙의 원하는 U 위치에 배치한다. 일괄 배치(BulkPlacePanel)를 사용하면 시작 U와 간격을 지정해 연속 배치할 수도 있다.
   - API: `POST /api/equipment/bulk-place`

5. **Digital Twin 확인** (`/digital-twin`): 평면도에서 방금 배치한 장비들이 즉시 반영된 것을 확인한다. 랙에 마우스를 올리면 서버 수, U 사용률, 호스트명 목록이 팝오버로 표시된다.

6. **모니터링 시작**: 별도 설정 없이, Prometheus 연동이 완료되면 대시보드(`/`)의 서버 가동 현황, CPU/메모리 Top 5, 클러스터별 필터에 24대가 자동으로 나타난다.

**소요 시간 비교**: 기존에 반나절 이상 걸리던 24대 입고 프로세스가, CSV 업로드 + 자동 탐지 + 드래그 배치로 약 30분 내 완료 가능하다.

[스크린샷: CSV 업로드 미리보기 화면 + 랙 드래그&드롭 배치 화면]

### 시나리오 C: "분기 용량 보고"

> *분기 말, 데이터센터 용량 현황과 향후 전망을 보고서로 제출해야 한다.*

**기존 방식**: 랙 사용률을 직접 세고 → 전력 사용량을 엑셀에서 계산하고 → 그래프를 그리고 → 워드 문서로 보고서 작성. 반나절~하루 소요.

**DC Express에서의 흐름**:

1. **용량 현황 확인** (`/capacity`): 한 화면에서 네 가지 용량 지표를 확인한다.
   - **공간**: 전체 U 수 대비 사용 U 수, 랙별 사용률
   - **전력**: 현재 소비 전력(Prometheus PCM 메트릭 합산) 대비 설비 용량
   - **냉각**: 냉각 설비 용량 대비 현재 발열
   - **컴퓨팅**: CPU/메모리 평균 사용률

2. **12개월 예측 확인** (같은 페이지): 장비 등록일(`createdAt`) 기반으로 월별 성장 추이 차트를 보여주고, 선형회귀로 12개월 후 예측값을 산출한다. "현재 추세라면 랙 공간은 몇 월에 소진되고, 전력은 몇 월에 한계에 도달한다"는 예측 카드가 표시된다.
   - API: `GET /api/capacity/forecast` (선형회귀 계산)

3. **리포트 생성** (`/reports`): 인프라 현황 + 알림 통계를 포함한 리포트 페이지에서 "PDF 다운로드" 버튼을 클릭한다. html2canvas + jsPDF로 A4 페이지네이션이 적용된 PDF가 생성되며, 한글 폰트도 정상 출력된다.

4. **제출**: 생성된 PDF를 그대로 보고서로 제출. 별도 문서 작성 없이 시스템이 생성한 리포트를 사용한다.

**소요 시간**: 용량 확인부터 PDF 생성까지 약 5분. 기존 반나절이 5분으로 단축된다.

[스크린샷: 용량 현황 대시보드 - 4개 용량 게이지 + 12개월 예측 차트]
[스크린샷: 생성된 PDF 리포트 첫 페이지]

## 5. 기술 아키텍처

### 시스템 구성도

DC Express는 Next.js 14 풀스택 모노레포 구조 위에, 4종의 이기종 데이터소스를 단일 웹 인터페이스로 통합한다.

```
┌─────────────────────────────────────────────────────────────────────┐
│                        사용자 브라우저                                │
│  React (App Router) + Zustand + Recharts + D3.js + SVG             │
└───────────┬───────────────────┬───────────────────┬─────────────────┘
            │ HTTP / SSE         │ HTTP REST          │ Next.js RSC
            ▼                   ▼                    ▼
┌───────────────────────────────────────────────────────────────────┐
│              Next.js API Routes (72개 엔드포인트)                   │
│  Zod 입력 검증 · RBAC 접근 제어 · 감사 로그 · JWT 인증              │
```

### 4종 데이터소스 연동 구조

| 데이터소스 | 용도 | 연동 방식 | 핵심 모듈 |
|-----------|------|----------|----------|
| **Prometheus** (Lab-1 + Lab-3) | CPU, 메모리, 온도, 전력, 네트워크 시계열 | PromQL HTTP API, SSE 15초 스트림 | `prometheus.ts` (590줄, 60+ 쿼리 정의) |

| **kube-state-metrics** | K8s Pod/Node 상태, 워크로드 현황 | Prometheus 경유 (PromQL) | `prometheus.ts` 내 kube 쿼리 |

### 핵심 기술 결정 3가지

**1. node-exporter 우선 + cAdvisor 폴백 (PromQL `or`)**

Prometheus 메트릭 조회 시 node-exporter를 먼저 쿼리하고, 결과가 없을 때만 cAdvisor로 폴백한다. node-exporter는 `IP:port` 형식 instance 라벨이라 DB의 장비 IP와 직접 매핑이 가능하고, cAdvisor는 `hostname` 형식이라 추가 변환이 필요하다. 이 전략은 초기에 cAdvisor만 사용하다가 매핑 불일치 문제를 반복적으로 겪은 뒤, 실측 데이터 확인을 거쳐 결정되었다.

**2. 폐쇄망 BMC 프록시**

Lab-1의 DCIM 앱에서 Lab-3 장비의 BMC(192.168.10.x 대역)에 직접 접근이 불가능하다. Lab-3 마스터 노드에 Python 기반 리버스 프록시(`bmc-proxy.py`)를 배치하여, HTTP 요청을 HTTPS BMC 호출로 변환한다. Room 모델에 `bmcProxyUrl` 필드를 두어 사이트별 프록시 주소를 설정할 수 있다.

**3. 듀얼 Prometheus 조회**

Lab-1(10.100.175.248:8080)과 Lab-3(10.144.131.190:30003) 두 클러스터의 Prometheus를 모두 조회한다. `instantQueryFrom()` 함수와 `source=lab3` API 파라미터로 클러스터별 메트릭을 분리하되, 대시보드에서는 All/Lab-1/Lab-3 탭으로 통합 조회도 지원한다.

## 6. 개발 과정: AI 협업(바이브 코딩) 경험

### 프로젝트 숫자

| 항목 | 수치 |
|------|------|
| 개발 기간 | 4.5개월 (2026-02-11 ~ 06-25), 실질 약 2.5개월 |
| 개발 인원 | 1명 (인프라 엔지니어, 웹 개발 비전공) |
| 총 커밋 | 513개 (AI 99%+) |
| 소스 코드 | 43,974줄 |
| 데이터 검증 스크립트 | 72개 작성, 29개 결과 기록 |

"바이브 코딩"이란 자연어로 AI에게 지시하면 AI가 코드를 작성하는 개발 방식이다. 개발자의 역할은 코드 작성이 아니라 기획, 방향 설정, 실환경 테스트, 데이터 확인이 된다.

### 7단계 진화 타임라인

| Phase | 시기 | 내용 | 커밋 | 교훈 |
|-------|------|------|------|------|
| 1. 스캐폴딩 | 4/8 (1일) | 프로젝트 구조, Prisma 스키마, 핵심 페이지 생성 | - | 사람이 며칠 걸릴 뼈대를 AI가 몇 시간에 |
| 2. Docker 삽질 | 4/9 (1일) | Alpine → Debian slim 전환 (Prisma OpenSSL 호환) | fix 5연속 | AI도 환경 차이는 부딪혀봐야 앎 |
| 3. 기능 폭발 | 4/10~20 | Prometheus, RBAC, CSV, SSE, i18n, 커맨드팔레트 | 주 30+ | 속도는 압도적. 단, 실데이터와 만나면 대거 수정 |
| 4. 실데이터 고통 | 4월 말~5월 중 | node-exporter 39커밋, BMC/Redfish 39커밋 | 78+ | "추측 코드 → 실패 → 재작성" 반복. Data-First 규칙 탄생 |
| 5. 규칙 정립 | 5월 중~말 | CLAUDE.md에 필수 규칙 축적, check/ 체계 정립 | - | 규칙 = 실패의 압축 |
| 6. 고도화 | 6월 | Digital Twin 편집, BMC 프록시, PUE, 다크모드, 조직 접근제어 | 171 (6월) | CLAUDE.md 덕에 실수 감소, AI 맥락 이해도 향상 |
| 7. 마무리 | 6/16~24 | 사용자 매뉴얼, PPT 56슬라이드, 결과보고서 | - | 문서화도 AI가 코드를 직접 읽고 작성 |

### fix가 feat의 2배인 현실

커밋 유형 분석 결과, fix 커밋(~120건)이 상당 비율을 차지한다. 바이브 코딩의 자연스러운 리듬은 "빠르게 만들고 → 실환경에서 깨지고 → 고치고"이다.

특히 Phase 4(실데이터 고통기)에서 이 패턴이 극심했다. Prometheus 쿼리를 `id="/"`로 작성했더니 K8s cAdvisor에서 root cgroup이 존재하지 않아 실패하고, cAdvisor의 hostname 형식 instance가 DB의 IP와 매핑되지 않아 실패하고, BMC Redfish 응답의 Systems 경로가 서버마다 달라서 실패했다. AI는 문서와 일반적 패턴으로 코드를 짜지만, 실제 인프라의 특수한 설정까지는 알 수 없다.

### CLAUDE.md: 실패가 만든 규칙

CLAUDE.md의 6개 필수 규칙은 모두 구체적인 실패 경험에서 탄생했다.

| 규칙 | 탄생 배경 |
|------|----------|
| **Data-First 개발** | Prometheus 쿼리를 추측으로 작성 → 실데이터에서 전부 실패. "실제 데이터 확인 후에만 코드 작성" 원칙 |
| **폐쇄망 제약 기록** | "결과를 파일로 push하세요"라고 안내 → "여기는 폐쇄망입니다" 답변. 사용자가 화면을 보고 손으로 타이핑해야 하는 제약 |
| **중복 구현 방지** | 세션 요약으로 이어지면서 AI가 이미 만든 기능을 다시 만듦. features.md를 단일 진실 공급원(SSOT)으로 지정 |
| **변경 영향 분석** | API 응답 구조 변경 → 프론트엔드 3곳 깨짐. 기능이 늘수록 연쇄 파급 증가 |
| **팀A/팀B 토론** | AI 단독 설계 판단 → 나중에 후회. 두 관점 비교 후 결정하는 프로세스 도입 |
| **검증 루틴** | tsc + test 통과 → 런타임 에러 발생. next build까지 실행해야 Server/Client 경계 문제를 잡을 수 있음 |

Data-First 규칙의 실체는 `check/` 디렉토리에 남아 있다. 72개의 확인 스크립트를 작성하고, 사용자가 폐쇄망 서버에서 실행한 결과를 손으로 타이핑하여 29개의 결과 기록으로 남겼다. 이 과정이 없었다면 추측 기반 코드 → 실패 → 재작성 사이클이 훨씬 길었을 것이다.

### 주요 피벗 사례

- **Docker Alpine → Debian Slim**: Prisma의 OpenSSL 의존성이 Alpine musl과 호환 불가. fix 3회 시도 후 베이스 이미지 자체 교체.
- **cAdvisor 전용 → node-exporter 우선**: 실측 후 node-exporter가 IP:port 형식이라 DB 매핑에 안정적임을 확인. PromQL `or` 연산자로 폴백 전략 확립.
- **hostname/IP 매핑 3곳 분산 → 통합**: 같은 매핑 로직이 흩어져 불일치 발생. `hostname-resolver.ts` 단일 모듈로 리팩터링.

## 7. 성과와 한계 — 솔직한 균형

### 성과

**비용 효율성.** AI 구독료 월 수십만 원 수준의 투자로, 외주 견적 수천만 원 ~ 1억 원급 시스템을 구축했다. 73개 API 엔드포인트, 29개 DB 모델, 39개 페이지, 4종 데이터소스 연동은 전문 웹 개발팀 3~4명이 6개월 이상 걸릴 규모다. 이것을 웹 개발 비전공자 1명이 2.5개월에 만들었다.

**속도.** 4.5개월간 513커밋. Phase 3(기능 폭발기)에는 주 30건 이상의 커밋을 기록했다. 매뉴얼 작성도 병렬 에이전트가 코드를 직접 읽어 하루 만에 완료했고, PowerPoint 56슬라이드도 자동 생성했다.

**기능 범위.** features.md 기준 12개 카테고리, 134개 이상의 기능 항목을 구현 완료했다. 대시보드, 서버 모니터링, 인프라 관리, 디지털 트윈, 랙 뷰, 알림, 용량 계획, 워크로드, 리포트, 설정까지 DCIM의 핵심 영역을 모두 커버한다.

**실사용 가능 수준.** Prometheus 자동 탐지로 서버 등록 → 실시간 모니터링 → BMC 원격 제어 → 알림 → 용량 예측 → PDF 리포트라는 엔드투엔드 워크플로가 실제로 동작한다. 조직별 접근 제어, 감사 로그, 가입 승인 시스템 등 엔터프라이즈 기능도 갖추었다.

### 한계 (숨기지 않는다)

**테스트 커버리지 부족.** 43,974줄의 코드에 테스트 파일은 8개(62개 테스트)뿐이다. 73개 API 라우트 중 테스트가 있는 것은 극소수다. 빌드가 통과해도 런타임 에러가 나는 경험을 여러 번 했다.

**fix 비율이 높다.** fix 커밋이 전체의 약 23%를 차지하는 것은, 초기 설계 부족과 추측 기반 코딩의 대가다. Phase 4의 Prometheus/BMC 연동에서만 78건 이상의 fix 커밋이 발생했다. Data-First 규칙을 처음부터 적용했다면 상당수를 줄일 수 있었다.

**리팩터링 부재.** 513커밋 중 refactor는 단 2건이다. 기능 추가에만 집중한 결과 코드 중복, 매핑 로직 분산 등 기술 부채가 축적되었다.

**프로덕션 빌드 미전환.** 현재 `npm run dev`(개발 모드)로 운영 중이다. dev 모드와 prod 모드는 완전히 다른 파이프라인이며, dev에서 안 나던 에러가 build에서 나는 것은 당연하다는 교훈을 얻었다.

**UI 디자인 통일 미완료.** PageHeader 컴포넌트 통일은 17개 페이지에 적용 완료했으나, Button 컴포넌트 교체, 카드/테이블 패딩 표준화 등 세부 디자인 토큰 정리는 진행 중이다.

### 바이브 코딩 조직 적용 제안

**적합한 영역:**
- 내부 관리 도구, 대시보드, PoC/프로토타입
- 도메인 전문가가 직접 자신의 도구를 만드는 경우
- 외부 노출이 없고, 보안 요구 수준이 상대적으로 낮은 시스템

**부적합한 영역:**
- 고객 대면 서비스 (UI 품질, 접근성, 성능 최적화 요구)
- 보안 민감 시스템 (인증/결제/개인정보)
- 높은 가용성이 필요한 프로덕션 서비스

**적용 시 필수 조건:**
1. **CLAUDE.md 규칙 체계**: 프로젝트 시작 시 배포 환경 제약, 코딩 규칙, 검증 절차를 문서화한다. 이 규칙은 실패할 때마다 추가되며, AI의 반복 실수를 방지하는 "프로젝트 헌법" 역할을 한다.
2. **Data-First 원칙**: 외부 시스템 연동 시 추측으로 코드를 짜지 않는다. 실제 데이터 구조를 먼저 확인하고, 확인 결과를 파일로 기록하여 재활용한다.
3. **도메인 지식을 가진 감독자**: AI는 코드를 빠르게 작성하지만, "이 방향이 맞는가?"라는 메타 판단은 사람이 해야 한다.
4. **features.md 같은 단일 진실 공급원**: AI가 세션 사이에서 맥락을 잃어도, 이 파일이 현재 상태를 알려준다. 기능 구현과 문서 갱신을 항상 동기화한다.
