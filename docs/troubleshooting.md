# Troubleshooting 이력

## 2026-04-22 ~ 04-28: 서버 상세 메트릭 차트 표시 안됨

### 증상
- 서버 상세 페이지에서 대부분의 차트가 데이터 없이 빈 카드로 표시
- 일부 차트만 간헐적으로 데이터 표시 (CPU Usage, Disk Usage 등 4-5개만)
- 브라우저 Console에 빨간색 hydration 에러

### 시도한 것들과 결과

| 날짜 | 시도 | 결과 |
|------|------|------|
| 04-22 | PromQL에 `on() group_left()` 조인 사용 | 실패 — 라벨 불일치로 빈 결과 |
| 04-22 | `sum()/sum()` 나누기로 변경 | 부분 성공 — Memory만 개선 |
| 04-22 | 모든 쿼리에 `sum()` 래핑 | 부분 성공 — 일부 차트만 |
| 04-22 | IP 기반 instance 해석 로직 추가 | 실패 — 불필요한 복잡성. 호스트네임 직접 사용이 정답 |
| 04-23 | Prometheus timeout 3초→10초 | 효과 없음 — timeout이 원인이 아니었음 |
| 04-23 | 에러 시 `setData([])` 제거 (데이터 유지) | 효과 없음 |
| 04-23 | ChartSkeleton `Math.random()` 제거 | hydration 에러 해결했지만 차트 문제와 무관 |
| 04-23 | useEffect `series` 의존성 → `seriesKey` 안정화 | 효과 미확인 — 차트 여전히 빈 상태 |
| 04-27 | `id="/"` → `container!=""` 변경 | **PromQL 쿼리는 해결** — check 스크립트에서 데이터 확인됨 |
| 04-28 | 디버그 표시 추가하여 프론트엔드 원인 진단 | pts=363 (121×3), 각 포인트에 시리즈 1개만 → **타임스탬프 불일치 확인** |
| 04-28 | 타임스탬프 정렬 `Math.round(ts/stepSec)*stepSec*1000` | **해결** — 멀티시리즈 차트 정상 표시 |
| 04-28 | 차트 애니메이션 비활성화 + connectNulls | **해결** — 재렌더 시 선 사라짐 방지 |

### 확인된 사실
1. **K8s cAdvisor에서 `id="/"` 는 존재하지 않음** — root cgroup이 없는 환경. `container!=""` 사용해야 함
2. **Prometheus API 응답에 데이터가 있음** (브라우저 Network 탭에서 확인) — 백엔드 문제 아님
3. **프론트엔드 렌더링에서 데이터가 차트로 변환되지 않음** — 원인 조사 중
4. **check 스크립트의 Prometheus URL 혼동** — Grafana(30004)와 Prometheus(ClusterIP 10.100.175.248:8080) 구분 필요

### 근본 원인 (해결됨)
1. **PromQL**: K8s cAdvisor에서 `id="/"`가 존재하지 않음 → `container!=""` 으로 교체
2. **차트 렌더링**: 멀티시리즈 차트에서 각 API 호출의 ms 단위 시간차로 타임스탬프 불일치. 3개 시리즈 × 121개 포인트 = 363개 포인트인데 각 포인트에 시리즈 1개만 존재 → Recharts가 선을 그릴 수 없음. `Math.round(ts / stepSec) * stepSec * 1000`으로 정렬하여 해결

### 교훈
- **Data-First**: 코드 작성 전에 반드시 실제 데이터 확인 (check 스크립트)
- **환경 차이 기록**: K8s cAdvisor의 cgroup 구조는 Docker standalone과 다름
- **URL 혼동 방지**: Grafana/Prometheus/앱 URL을 CLAUDE.md에 명확히 분리 기록
- **한 번에 하나씩**: 전체를 한꺼번에 고치려 하지 말고 메트릭 하나씩 확인

## 2026-06-22: 프로덕션 빌드 전환 실패 (dev → prod)

### 증상
- `sudo bash scripts/switch-prod.sh` 실행 후 서비스 반복 재시작
- `dcim.service: Failed with result 'exit-code'`
- `Main process exited, code=exited, status=1/FAILURE`

### 이 문제는 복잡했는가? — 아니다.

**객관적으로 단순한 문제 2개**였다:
1. ISR 페이지 3개가 빌드 시 DB 프리렌더링 시도 → `force-dynamic` 추가 (Next.js 기본 지식)
2. `@types/pako` 간접 의존성이 서버에서 깨짐 → `tsconfig.json`에 `types` 명시 (TypeScript 기본 지식)

그런데 **해결까지 4번의 시도, 12개 이상의 에이전트, 수시간**이 걸렸다.

### 시도한 것들과 결과

| 시도 | 결과 | 잘못된 이유 |
|------|------|-------------|
| 1차: BUILD_ID 조건 수정 (`-d .next` → `-f .next/BUILD_ID`) | 실패 — 같은 에러 반복 | **증상 치료**: 빌드 실행 조건은 맞았지만, 빌드 자체가 실패하는 원인은 건드리지 않음 |
| 2차: ISR 페이지 force-dynamic 변경 (에이전트 4명) | 부분 성공 — ISR 에러는 해결 | **범위 부족**: 이것만 고치고 "빌드 성공"을 선언했지만, 서버 환경의 다른 에러를 확인 안 함 |
| 3차: pako 타입 에러 발생 | 실패 — 새 에러 등장 | **환경 차이 간과**: 개발 환경에서 빌드 성공 확인 후 푸시했지만, 서버의 node_modules 상태가 다름 |
| 4차: tsconfig types 명시 (에이전트 8명) | 성공 | 전체 타입 체계를 조사해서 근본 해결 |

### 왜 여러 차례 시도가 필요했는가 — AI의 문제 해결 패턴 분석

**1. "증상 → 원인" 방향으로만 추론했다**

에러 메시지(exit code 1, BUILD_ID 없음)만 보고 바로 코드를 고쳤다. "이 빌드가 성공하려면 어떤 전제 조건이 필요한가?"라는 역방향 질문을 하지 않았다. 역방향으로 생각했다면 첫 시도에서 ISR + 타입 + 환경 차이를 모두 발견했을 것이다.

**2. "한 가지 고치고 → 다음 에러 발견" 루프에 빠졌다**

한 번에 모든 잠재적 문제를 조사하지 않고, 발견한 문제 하나만 고친 뒤 "됐다"고 선언했다. 서버에서 실행 → 새 에러 → 또 고침 → 또 새 에러. 이것이 사용자 시간을 가장 많이 낭비한 패턴이다.

**3. "개발 환경 빌드 성공 = 서버에서도 성공"이라고 가정했다**

개발 환경에서는 `@types/pako`가 정상 설치되어 있었다. 서버의 node_modules 상태가 다를 수 있다는 것을 고려하지 않았다. 폐쇄망 환경에서 파일을 복사하는 방식이므로 node_modules 차이가 발생할 수밖에 없다.

**4. 개발 모드와 프로덕션 모드의 차이를 처음부터 설명하지 않았다**

`npm run dev`는 SWC 기반 빠른 변환만 수행하고 전체 타입 검사를 하지 않는다. `npm run build`는 전체 TypeScript 컴파일 + ISR 프리렌더링 + 타입 검사를 수행한다. 이 차이를 처음부터 분석했으면 "dev에서 안 나던 에러가 build에서 나는 것은 당연하다"는 전제로 시작할 수 있었다.

### 근본 원인 (해결됨)

| 원인 | 수정 | 파일 |
|------|------|------|
| ISR 페이지(`/racks`, `/reports`, `/infrastructure`)가 빌드 시 DB 쿼리 실행 | `revalidate` → `force-dynamic` 변경 | 5개 page.tsx |
| TypeScript가 `node_modules/@types/`의 모든 패키지를 자동 로드 → 서버에서 `@types/pako` 비정상 시 실패 | `tsconfig.json`에 `types: ["node", "react", "react-dom", "d3", "bcryptjs"]` 명시 | tsconfig.json |

### 개발 모드에서 에러가 안 났던 이유

| 항목 | `npm run dev` (개발) | `npm run build` (프로덕션) |
|------|------|------|
| TypeScript 검사 | SWC 변환만 (타입 검사 안 함) | 전체 tsc 컴파일 + 타입 검사 |
| ISR 프리렌더링 | 안 함 (모든 페이지 요청 시 렌더링) | 빌드 시 정적 페이지 프리렌더링 시도 |
| @types 자동 발견 | 검사 안 하므로 문제 안 됨 | 전체 스캔 → 깨진 @types 발견 시 실패 |
| DB 필요 | 요청 시에만 | ISR 페이지는 빌드 시점에도 필요 |

### 교훈 — 이 사례에서 배울 것

1. **"됐다" 선언 전에 서버 환경을 시뮬레이션하라**: 개발 환경 빌드 성공은 절반의 검증. 서버의 node_modules, 환경변수, TypeScript 설정이 다를 수 있다.
2. **첫 시도에서 모든 잠재 문제를 조사하라**: 에러 하나 고치고 "해결"이 아니라, "이 빌드가 실패할 수 있는 모든 경로"를 한번에 점검해야 한다.
3. **dev → prod 전환은 별도 단계로 취급하라**: 개발 모드와 프로덕션 모드는 완전히 다른 파이프라인이다. 전환 시 체크리스트가 필요하다.
4. **AI의 "고쳤습니다" 선언을 신뢰하지 마라**: AI는 자신이 고친 부분만 확인한다. 전체 그림을 보는 것은 사람의 역할이다.

### dev → prod 전환 체크리스트 (이 경험에서 도출)

- [ ] 모든 DB 접근 페이지에 `force-dynamic` 확인
- [ ] `tsconfig.json`에 `types` 명시적 설정 확인
- [ ] `npm run build` 로컬 성공 확인
- [ ] 서버 node_modules 상태 확인 (`npm install` 필요 여부)
- [ ] 환경변수 (`DATABASE_URL`, `NEXTAUTH_SECRET`) 빌드 전 설정 확인
- [ ] `scripts/rebuild-prod.sh`로 전체 과정 자동화
