## 보고서 구조 (A4 약 7-8페이지)

### 1. Executive Summary (0.5p)

3줄 요약: 누가(1인+AI), 왜(Grafana 한계), 뭘 만들었고(DCIM 웹앱), 핵심 성과는(38페이지, 68 API, 29 DB 모델).

### 2. 배경: 왜 만들었나 (1p)

- Grafana 대시보드 10개 이상 산재 → 한 화면에서 전체 파악 불가
- 자산 관리(장비 위치, 라이프사이클, 보증 만료)를 엑셀/메모로 관리하던 문제
- 물리적 배치(어느 랙 몇 U)를 머릿속으로만 기억하던 문제
- 전담 웹 개발자 없이 인프라 엔지니어가 직접 개발해야 하는 상황
- 외주 비용 대비 AI 협업 개발이라는 새로운 가능성

### 3. Before/After 비교 (1p)

| 항목 | Before (Grafana) | After (DC Express) |
|------|------------------|--------------------|
| 모니터링 | 분산된 대시보드 | 통합 38페이지 |
| 자산 관리 | 엑셀/수기 | DB 기반 CRUD + 라이프사이클 |
| 물리 배치 | 기억 의존 | Digital Twin + 랙 다이어그램 |
| 알림 | Grafana 알림 | 커스텀 규칙 + 이력 + 만료 추적 |
| 용량 계획 | 없음 | 12개월 예측 + PDF 리포트 |
| BMC 제어 | 별도 IPMI 접속 | 웹에서 원격 전원 제어 |
| K8s 워크로드 | kubectl CLI | 웹 UI 통합 |

### 4. 주요 기능과 사용 시나리오 (1.5p)

**시나리오A "새벽 3시 서버 장애"**
알림 확인 → 대시보드에서 이상 서버 클릭 → CPU/메모리/온도 확인 → BMC 원격 재시작 → 복구 확인. 모두 한 화면에서.

**시나리오B "장비 24대 입고"**
CSV 일괄 등록 → 랙 위치 배정 → Prometheus 자동 탐지로 모니터링 시작 → Digital Twin에 즉시 반영

**시나리오C "분기 용량 보고"**
용량 현황 대시보드 → 12개월 선형 회귀 예측 → PDF 리포트 생성 → 그대로 제출

### 5. 기술 아키텍처 (1p)

- 시스템 구성도 1장 (Next.js + Prometheus + PostgreSQL + BMC/Redfish + K8s)
- 4종 데이터소스 연동 구조
- 68개 API, 29개 DB 모델, SSE 실시간 스트림
- node-exporter 우선 + cAdvisor 폴백 전략
- 폐쇄망 BMC 프록시 구현
- 참고: docs/technical-data-flow.md, docs/data-flow-diagram.html

### 6. 개발 과정: AI 협업(바이브 코딩) 경험 (1.5p)

- 439커밋(AI 99.3%), 42,333줄, 1인 개발
- 7단계 타임라인 (스캐폴딩 1일 → 기능폭발 → 실데이터 고통 → 안정화)
- fix가 feat의 2배인 현실 (110 vs 55): "빠르게 만들고 → 실데이터에서 깨지고 → 고치는" 사이클
- CLAUDE.md 6개 규칙이 각각 어떤 실패에서 탄생했는지
- 피벗 사례: Alpine→Debian, cAdvisor→node-exporter, hostname 분산→통합
- 참고: docs/retrospective-prep.md

### 7. 성과와 한계 — 솔직한 균형 (1p)

**성과:**
- 비용 효율: AI 구독 수십만 원 vs 외주 수천만 원급 시스템
- 속도: 일 평균 6커밋, 주요 기능 2.5개월 내 구축

**한계 (숨기지 않는다):**
- 테스트 커버리지 부족 (7개 테스트 파일 / 42K줄)
- fix가 feat 2배 → 초기 설계 부족의 대가
- 프로덕션 빌드 미전환 (현재 dev 모드)
- Multi-Prometheus 미연동 (Lab-3 인프라 복구 필요)

### 8. 향후 계획 + 조직 적용 제안 (0.5p)

**남은 작업:**

| 항목 | 설명 | 우선순위 |
|------|------|----------|
| 프로덕션 빌드 전환 | dev → build + start | 높음 |

**바이브 코딩 조직 적용:**
