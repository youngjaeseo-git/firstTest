## 3. 프로젝트 진화 타임라인

### Phase 1: 스캐폴딩 (4/8, 하루)
- 프로젝트 구조, Prisma 스키마, Phase 1/2 핵심 페이지 한번에 생성
- **교훈**: AI가 초기 뼈대를 몇 시간 만에 세워줌. 사람이 하면 며칠 걸릴 작업.

### Phase 2: Docker 삽질 (4/9, 하루)
- Alpine → Debian slim 전환 (Prisma OpenSSL 호환 문제)
- 연속 5개 fix 커밋
- **교훈**: AI도 환경 차이는 맞닥뜨려봐야 안다. Docker 빌드 실패를 3번 겪은 뒤 해결.

### Phase 3: 기능 폭발기 (4/10~4/20)
- Prometheus 연동, RBAC, CSV 임포트, SSE 스트림, i18n, 커맨드팔레트
- 일주일에 30+ 커밋
- **교훈**: 기능 추가 속도는 압도적. 하지만 이때 만든 것들이 실 데이터와 만나면서 Phase 4에서 대거 수정됨.

### Phase 4: 실 데이터 고통기 (4월 말~5월 중)
- node-exporter 트러블슈팅만 39커밋
- PCM 메트릭 Job 이름 오타 수정 3커밋, instance 필터 방식 4번 변경
- BMC/Redfish 연동 39커밋
- **교훈**: 가장 힘든 구간. "추측으로 만들고 → 실 데이터에서 깨지고"를 반복. 이 경험이 Data-First 규칙을 만들어냄.

### Phase 5: 규칙 정립기 (5월 중~말)
- CLAUDE.md에 필수 규칙 축적 (팀A/B 토론, 중복 확인, 영향 분석, 검증 루틴)
- check/ 디렉토리 체계 정립
- **교훈**: 규칙은 "통제"가 아니라 "실패의 압축". 매번 삽질할 때마다 재발 방지 규칙이 하나씩 추가됨.

### Phase 6: 고도화 (6월)
- Digital Twin 편집 모드, 바닥평면도, Lab-3 24대 벌크 등록
- BMC 프록시 구현 (폐쇄망 대응)
- 대시보드 리디자인, PUE 위젯, 테마 토글
- **교훈**: 이 시점이 되면 AI가 프로젝트 맥락을 잘 이해하고, CLAUDE.md 규칙 덕분에 실수도 줄어듦.

### Phase 7: 마무리 (6/16~17)
- 사용자 매뉴얼 작성 (4명 에이전트 병렬)
- PowerPoint 56슬라이드 자동 생성
- **교훈**: 문서화도 AI가 코드를 직접 읽고 작성. 사람이 하면 1주일 걸릴 매뉴얼을 하루 만에.

## 5. CLAUDE.md 규칙의 탄생 배경 (문제 → 규칙)

| 규칙 | 어떤 문제에서 탄생했나 |
|------|------------------------|
| **Data-First 개발** | Prometheus 쿼리를 `id="/"`로 작성 → K8s cAdvisor에서 root cgroup이 없어서 실패. 추측으로 코드를 짜면 반드시 깨진다는 교훈 |
| **폐쇄망 제약 기록** | 사용자에게 "결과를 파일로 push하세요"라고 안내 → 사용자가 "그게 안 됩니다, 여기는 폐쇄망입니다"라고 답변. 환경 제약 미인지 |
| **중복 구현 방지** | 세션이 요약본으로 이어지면서 이미 만든 기능을 AI가 다시 만듦. features.md를 single source of truth로 지정 |
| **변경 영향 분석** | API 응답 구조를 바꿨는데 프론트엔드 3곳이 깨짐. 기능이 많아질수록 연쇄 파급 효과 증가 |
| **팀A/팀B 토론** | 설계 판단을 AI 단독으로 진행 → 나중에 "다른 방법이 나았겠다"는 후회. 두 관점 비교 후 결정 |
| **검증 루틴** | tsc 통과 + 테스트 통과 → 런타임 에러 발생. next build까지 해야 Server/Client 경계 문제를 잡을 수 있음 |

## 6. 주요 기술적 피벗 사례

### 6.1 Docker Alpine → Debian Slim
- **문제**: Prisma의 OpenSSL 의존성이 Alpine musl과 호환 안됨
- **시도**: 3번의 fix 시도 (라이브러리 추가, 빌드 옵션 변경)
- **결론**: 베이스 이미지 자체를 교체
- **교훈**: AI가 "이 이미지가 더 낫다"고 처음부터 알려주진 않음. 부딪혀봐야 알게 됨.

### 6.2 cAdvisor 전용 → node-exporter 우선
- **문제**: cAdvisor는 hostname 형식 instance, node-exporter는 IP:port 형식
- **발견**: 실측 후 node-exporter가 더 안정적 매핑 가능
- **결론**: `or` 연산자로 node-exporter 우선 + cAdvisor 폴백 전략
- **교훈**: Data-First 규칙의 직접적 계기

### 6.3 hostname/IP 매핑 분산 → 통합
- **문제**: 3곳에 같은 매핑 로직이 흩어져 있어 하나를 바꾸면 다른 곳이 불일치
- **결론**: `hostname-resolver.ts` 단일 모듈로 리팩터링
- **교훈**: 바이브 코딩에서 "빨리 만들기"에 집중하면 자연스럽게 중복이 생김. 주기적 정리 필요.

### 6.4 dev → prod 빌드 전환 삽질 (06-22)
- **문제**: 개발 모드 → 프로덕션 전환 시 `npm run build` 실패. 서비스 재시작 루프
- **시도 횟수**: 4번, 에이전트 총 12명 이상 투입, 수시간 소요
- **진짜 원인**: ISR 페이지 3개가 빌드 시 DB 접근 + `@types/pako` 서버에서 깨짐
- **왜 오래 걸렸나**: 증상(exit code 1)만 보고 코드를 고침. "빌드가 성공하려면 어떤 전제 조건이 필요한가?"를 물어야 했는데 "이 에러를 어떻게 고치지?"만 물었다
- **교훈**: 에러 하나 고치고 "해결" 선언이 아니라, 가능한 모든 실패 경로를 한번에 조사해야 한다. 이것은 회고 11장 "미로찾기" 패턴의 실제 사례
- **추가 교훈**: dev 모드와 prod 모드는 완전히 다른 파이프라인이다. dev에서 안 나던 에러가 build에서 나는 것은 당연하다

### 6.5 CLAUDE.md 비대 → docs/ 분리
- **문제**: CLAUDE.md에 인프라 정보, 쿼리 규칙 등이 과도하게 축적
- **결론**: `docs/infrastructure.md`로 분리
- **교훈**: CLAUDE.md는 "규칙"만 담고, "데이터"는 별도 문서로

### "4개월간 혼자서 4.2만 줄?"
- AI가 99.3%의 커밋을 작성
- 사람의 역할: 기획, 방향 설정, 실환경 테스트, 데이터 확인, 결과 타이핑
- AI의 역할: 코드 작성, 디버깅, 문서화, 리팩터링, 번역

### "만능이 아니다 — 현실과 부딪히면 깨진다"

- Docker Alpine→Debian, cAdvisor→node-exporter 등 피벗 다수
- AI는 "추측"으로 코드를 짠다. 실 데이터를 모르면 틀린 코드가 나옴

### "규칙으로 AI를 길들여야 한다"

- Data-First = 추측 금지. 실제 데이터 확인 후에만 코드 작성

### "폐쇄망이라는 특수한 도전"
- 결과를 파일로 반출할 수 없음 → 사용자가 화면을 보고 손으로 타이핑

- 이 제약이 Data-First 규칙의 스크립트 설계 원칙을 만들어냄

## 10. 가장 큰 깨달음 — "프롬프트로 버텼지만, 도구로 박았어야 했다"

회고하면서 글로는 정리됐지만 한 단어로 안 잡히던 무언가의 정체:

> **나는 모든 규칙을 "말(프롬프트)"로 유지해왔다.**
> 말은 매번 다시 해야 하고, 세션이 바뀌면 사라지고, 조금씩 변형된다.
> Claude Code의 기능들은 전부 "매번 말하던 것을 파일로 고정하는 것"이다.

### 증거는 프로젝트 안에 이미 있었다

| 신호 | 의미 |
|------|------|
| **CLAUDE.md를 25번 수정** | 규칙을 손으로 계속 다듬어왔다 = 자동화되지 않은 규칙 |
| **팀A/팀B를 매번 프롬프트로 호출** | 가장 자주 쓰는 프로세스인데 매번 새로 생성 |
| **fix 커밋이 feat의 2배** | 검증을 매번 수동으로 → 빠뜨림 → 깨짐 → 고침 |
| **폐쇄망 확인 스크립트 매번 수작업** | Data-First 규칙이 텍스트로만 존재 |

### 다음엔 이렇게 — 3가지 도구화

#### ① 팀A/팀B → 서브에이전트 (`.claude/agents/`)
- **현재 문제**: 설계 판단마다 팀A/팀B를 프롬프트로 새로 호출. 토큰·시간 소모, 관점이 매번 조금씩 변형됨
- **개선**: `team-a`, `team-b`, `impact-analyzer`를 파일로 정의 → 호출만 하면 됨. 독립 컨텍스트라 메인 대화도 안 더럽혀짐
- **이 프로젝트 효과**: "변경 영향 분석" 누락(API 바꿨더니 프론트 3곳 깨짐)을 `impact-analyzer`가 Grep으로 자동 점검 → fix 커밋 감소

#### ② 검증 루틴 → 훅 (Hook, `PostToolUse`)
- **현재 문제**: "코드 작성 후 `npm run verify` 필수"를 CLAUDE.md에 써놓고 매번 손으로 실행 → 빠뜨림
- **개선**: Edit/Write 후 자동으로 typecheck·lint 실행되도록 훅으로 박음
- **이 프로젝트 효과**: fix가 feat의 2배인 가장 직접적 원인(검증 누락)을 기계가 강제 → 런타임 에러 조기 발견

#### ③ Data-First / features.md 동기화 → 스킬 (Skill, `.claude/skills/`)
- **현재 문제**: "확인 스크립트 만들기", "features.md 갱신"의 절차가 고정인데 매번 설명·수작업
- **개선**: 슬래시 커맨드로 호출. 폐쇄망 출력 최소화 규칙까지 스킬 안에 박아둠
- **이 프로젝트 효과**: features.md 누락(중복 구현)·장황한 스크립트 출력(타이핑 부담)을 절차로 고정

> **폐쇄망 주의**: MCP(Prometheus/DB 직접 연결)는 망 제약으로 우선순위 낮음.
> 이 프로젝트엔 **Hook + Skill + Subagent** 조합이 정답에 가깝다.

## 11. 미로찾기와 AI — "막다른 길을 인지하는 능력"

> **이미지**: [docs/images/maze-metaphor.svg](images/maze-metaphor.svg)

### 신문 미로 vs 현실 미로

신문이나 퍼즐책의 미로찾기를 생각해보자. 시작점과 목표점이 한눈에 보인다. 우리는 자연스럽게 **목표에서 거꾸로** 올라가면서 경로를 찾는다. 갈림길에서 어디로 가야 하는지 이미 알고 있다. 틀릴 일이 거의 없다.

그런데 우리가 AI를 사용하면서 겪는 현실은 **전혀 다른 종류의 미로**다.

- 목표점이 안개 속에 있다. 대략적인 방향만 있을 뿐 정확한 위치를 모른다.
- 지금 서 있는 곳 주변만 보인다. 전체 지도가 없다.
- 갈림길에서 오른쪽이 맞는지 왼쪽이 맞는지 **확률적으로** 선택해야 한다.
- 운 좋게 올바른 방향으로 갈 수도 있고, 완전히 잘못된 방향으로 갈 수도 있다.

### 가장 위험한 순간: "잘못된 길의 깊은 곳"

문제는 **아예 잘못된 방향으로 깊이 들어갔을 때** 벌어진다.

그 막다른 길 안에서 나름대로 방향을 바꿔보고, 다른 기술을 시도해보고, AI에게 다른 질문을 던져본다. 하지만 **근본적인 출발점 자체가 틀렸기 때문에** 그 안에서 아무리 발버둥쳐도 해결되지 않는다.

이것이 AI 사용에서 **가장 난감하고 짜증나는 순간**이다:

- 하루, 이틀 같은 문제를 해결하지 못하면서 AI와 대화를 계속한다
- 토큰과 비용이 계속 쌓인다
- 시간이 흘러간다
- 스트레스가 머리끝까지 올라간다
- 그런데도 진전이 없다

### 이 프로젝트에서의 실제 사례

이번 **프로덕션 빌드 실패**가 정확히 이 패턴이었다:

1. "빌드가 실패한다" → BUILD_ID 조건을 고쳤다 → 여전히 실패
2. 에이전트 4명 투입 → ISR 프리렌더링 발견, 고쳤다 → "해결" 선언
3. 서버에서 실행 → **pako 타입 에러**라는 전혀 새로운 에러 등장
4. 에이전트 8명 투입 → tsconfig types 명시로 해결

**객관적으로 단순한 문제 2개**(force-dynamic 추가, types 명시)인데 4번 시도, 에이전트 12명, 수시간이 걸렸다. 이유:
- AI가 "이 에러를 어떻게 고치지?"만 물었다 (증상 치료)
- "빌드가 성공하려면 어떤 전제 조건이 필요한가?"를 물어야 했다 (구조 분석)
- 한 가지 고치고 "됐다" 선언 → 서버에서 새 에러 → 또 고침의 루프
- 개발 환경과 서버 환경의 차이(node_modules 상태, TypeScript 검사 범위)를 고려하지 않았다

이것이 "미로의 잘못된 갈래"다. BUILD_ID 조건을 아무리 잘 고쳐도, 그것은 진짜 원인이 아니었다. 하나를 고쳐도 전체를 보지 않으면 다음 벽에 부딪힌다.

(상세 트러블슈팅 기록 → [docs/troubleshooting.md](troubleshooting.md) "2026-06-22: 프로덕션 빌드 전환 실패" 참조)

### 그래서 어떻게 해야 하는가?

이 질문이 **AI를 잘 쓸 수 있는 핵심 지점**이라고 생각한다. 개인적인 접근과 AI 활용 관점을 함께 정리했다.

#### 원칙 1: "같은 자리를 3번 맴돌면 멈춰라"

같은 에러가 3번 반복되거나, 비슷한 시도를 3번 해서 안 되면 — **더 시도하지 말고 멈춘다**. 그 시점에서 AI에게 계속 물어보는 것은 "같은 막다른 길 안에서 벽을 더 세게 치는 것"과 같다.

#### 원칙 2: "AI를 바꾸지 말고, 질문을 바꿔라"

막혔을 때 흔한 실수는 "다른 AI를 써볼까?", "프롬프트를 더 길게 써볼까?"이다. 하지만 문제는 AI가 아니라 **내가 서 있는 위치**다.

- **나쁜 질문**: "이 에러를 어떻게 고치지?" (증상에 집중)
- **좋은 질문**: "이 기능이 동작하려면 어떤 전제 조건이 필요하지?" (구조에 집중)
- **더 좋은 질문**: "이 접근 자체가 맞는지 다른 관점에서 검증해줘" (방향 전환)

#### 원칙 3: "사람이 방향을 잡고, AI가 실행한다"

AI는 **주어진 맥락 안에서** 최선을 찾는 데 탁월하다. 하지만 **"지금 우리가 잘못된 길에 있다"는 판단**은 사람이 해야 한다. AI는 미로 안에서 벽을 피하는 건 잘하지만, "이 미로 자체를 나가야 한다"는 메타 판단은 잘 못한다.

실제로 이번 빌드 문제에서:
- AI에게 "빌드 에러 고쳐줘"라고 하면 → 증상만 계속 치료한다
- AI에게 "빌드가 실패할 수 있는 **모든 가능한 원인**을 조사해줘"라고 하면 → 4개 에이전트가 각자 다른 각도로 조사해서 **진짜 원인(ISR 프리렌더링)을 찾아냈다**

차이는 AI의 능력이 아니라 **사람이 던진 질문의 범위**였다.

#### 원칙 4: "새 세션이 때로는 최고의 해결책이다"

긴 대화에서 AI도 맥락에 갇힌다. 이전에 시도한 것들의 맥락이 쌓이면서 같은 패턴을 반복하게 된다. 새 세션을 열어서 처음부터 문제를 설명하면, AI가 **선입견 없이** 다른 접근을 제시하는 경우가 많다.

이것은 사람도 마찬가지다 — 하루 종일 같은 버그와 씨름하다가, 다음날 아침에 샤워하면서 "아, 그거였구나" 하는 경험이 누구나 있다.

### 결론: AI를 잘 쓰는 사람은 "멈출 줄 아는 사람"

| 상황 | AI에게 맡기기 | 사람이 직접 판단 |
|------|:---:|:---:|
| 코드 작성, 디버깅 | O | |
| 에러 원인 분석 (범위가 좁을 때) | O | |
| **같은 문제가 3번 이상 반복** | | O — "방향이 맞는가?" |
| **해결 방법을 여러 번 바꿔도 진전 없음** | | O — "전제가 틀렸는가?" |
| 새로운 접근 방식 탐색 | O (새 세션, 넓은 질문) | O (경험 기반 직관) |
| **"더 이상 이 안에서는 답이 없다" 판단** | | O — 이것이 핵심 |

> **"미로의 막다른 길을 인지하는 것"은 AI가 아니라 사람의 몫이다.**
> **그리고 되돌아가는 용기가 있을 때, 가장 빠르게 목표에 도달한다.**
